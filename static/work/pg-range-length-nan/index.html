NaN range lengths and 1e100-row estimates

Ruohang Feng (Vonng@PGSTY) · rh@vonng.com · 17 October 2026 · Patch proposed on pgsql-bugs, not committed

ANALYZE stores the result of the range subtype's subdiff function as the length of each range. For numeric that is NaN for some valid ranges, such as [1,NaN) and [Infinity,Infinity]. Once a NaN is in the length histogram, <@ and @> can get a NaN selectivity, and clamp_row_est() turns it into an estimate of 1e100 rows. Query results are correct, but plans built on these estimates can be very slow. No statistics import is involved: ordinary data and ANALYZE (or autovacuum) are enough.

Affected
<@ and @> on numrange; on nummultirange with a multirange, and @> with a range; float8-based range types. The code is from 9.3 (59d0bf9dca).
Effect
1e100-row estimates; in the join below, 2,000,000 index probes instead of 151, about 4 s instead of 65 ms.
Fix
get_len_position() returns 0.5 when either bin boundary is NaN, in the range and multirange code. One check with a comment in each file; histograms without NaN entries are not affected.
Tested
14, 18, 19rc1 and master on Linux x86_64; 18, 19 and master on macOS aarch64. Assertions enabled.

Reproducer

In a fresh database:

INSERT INTO nan_len SELECT g, numrange(g, g + (g % 97) + 1)
  FROM generate_series(1, 1000) g;
INSERT INTO nan_len SELECT 1000 + g, numrange(g, 'NaN')
  FROM generate_series(1, 20) g;

[Infinity,Infinity] is a nonempty range whose bounds are the value Infinity, not unbounded, so ANALYZE calls subdiff and gets Infinity − Infinity = NaN. An unbounded range such as numrange(g, NULL) gets the length Infinity without calling subdiff, and does not trigger the problem. The multirange <@ range estimate is too high without NaN being involved, and the patch does not change it.

Cause

  1. compute_range_stats() (rangetypes_typanalyze.c) stores subdiff(upper, lower) as the length of each bounded range, without checking it. numrange_subdiff() returns NaN for a NaN bound and for Infinity − Infinity. The built-in integer, date and timestamp range types cannot produce NaN.
  2. The lengths are sorted with float8_qsort_cmp(), which uses plain C comparisons and so reports “greater” whenever either argument is NaN. That is not a consistent order, and NaN entries can end up anywhere in the array. Most land at the end, and the last element is always kept in the histogram.
  3. length_hist_bsearch() returns the last entry less than the searched length. NaN < x is false, so it can stop on a bin whose upper boundary is NaN.
  4. get_len_position() interpolates in that bin: 
    if (!isinf(hist1) && !isinf(hist2))
{
    if (isinf(value))
        return 0.5;

    return 1.0 - (hist2 - value) / (hist2 - hist1);    /* NaN */
}
    calc_length_hist_frac() then returns NaN, and so does the selectivity of <@ and @>.
  5. CLAMP_PROBABILITY() tests p < 0.0 and p > 1.0, both false for NaN, so NaN passes. So does the range check in restriction_selectivity().
  6. clamp_row_est() maps a NaN row count to MAXIMUM_ROWCOUNT, 1e100.

Commit 652686a334 (2020, bug #16122, back-patched to all branches then supported) made get_position() and get_distance() punt on NaN from subdiff for the bounds histogram. The length histogram side never got the same treatment.

The patch also adds a regression test to rangetypes.sql. It builds a numrange table with NaN-bound and [Infinity,Infinity] rows and a nummultirange copy, checks that the length histogram contains NaN, and checks that four <@/@> estimates do not exceed the row count. All four estimate checks fail without the C change.

Why this is enough

  • It is the only place that can see a NaN. get_len_position() is where calc_length_hist_frac() does arithmetic on histogram entries. Its other use of them is the loop over the bins, which compares bin_upper < length2; that comparison is false for NaN, so the loop stops at a NaN entry. The lower boundary of the first bin is never NaN, because the binary search only stops on an entry that compared less than the searched length. It can be NaN in the last bin, when the search falls before the first entry and the histogram starts with NaN. Hence both boundaries are checked.
  • Nothing else can become NaN. Without the NaN entries, an ANALYZE-built histogram is still sorted. sort_template.h compares elements only with the pivot during partitioning, and with a neighbour during insertion sort. A non-NaN pivot places the non-NaN values on the correct side; a NaN pivot sends everything else to one side; insertion sort never moves a value past a smaller non-NaN one. A sorted histogram cannot produce Infinity − Infinity or a zero-width bin in this code.
  • Measured. On 60 ANALYZE-built tables (numrange, nummultirange and a float8 range; NaN rows, [Infinity,Infinity] rows and unbounded rows; statistics targets 10 to 300; NaN entries at the start, in the middle and at the end of the histogram), 229 of 720 <@ and @> estimates were 1e100 without the patch and none with it. On 19rc1, a more defensive variant that also clamps the interpolated position and the final fraction gave the same estimate for all 720 queries.

What does not change

  • Histograms without NaN entries. The new branch is never taken. 400 random <@, @> and && queries over int4range, numrange, daterange, tstzrange, int4multirange and int4range with unbounded values gave identical estimates with and without the patch.
  • Existing statistics. Nothing in the catalog changes, and no new ANALYZE is needed. The before/after numbers in this report come from the same data directory, started first with the unpatched and then with the patched binary; a hash of the fixtures' pg_stats rows was identical.
  • ANALYZE, sorting and statistics import. These are untouched. The patch handles histograms as ANALYZE builds them; it does not try to validate length histograms supplied by hand through pg_restore_attribute_stats().

0.5 is a fallback, not an estimate of the true position. Apart from the 229 cases that went from 1e100 to a finite value, 62 estimates changed that had been finite but were still computed from NaN intermediate values. 52 of these moved closer to the actual row count and 10 moved further away.
