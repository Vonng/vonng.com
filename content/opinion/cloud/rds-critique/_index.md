云 RDS 绝非数据库工程的巅峰，而是按核数线性收租、溢价十余倍的“及格线预制菜”。它因畏惧 AGPLv3 传染而阉割 PostgreSQL 扩展灵魂，又以黑盒管控剥夺用户知情权，在故障时屡屡把小卡顿放大成断服惨案。

## 一、十倍溢价与被阉割的扩展灵魂 {#rds-scam-and-castration}

### 为什么说云 RDS 是用米其林价格吃预制菜？ {#rds-overpriced-premade}

云 RDS 本质是把廉价硬件套上闭源管控、按核数线性收租的暴利游戏。IDC 托管两三台 64C 企业级 NVMe 物理机组高可用，五年折旧年均仅 3～4.5 万元；同级 RDS 在阿里云却要 25～76.5 万元，AWS 更达 160～217 万元，溢价高达 7～50 倍。企业数据库一旦跨过 100 核拐点，省下的纯管控税就够养活专职 DBA 并大幅净赚。

### 抛开十倍溢价，云 RDS 的性能与监控够专业吗？ {#rds-mediocre-quality}

云 RDS 充其量只是“及格线上的大锅饭”，远称不上专业巅峰。本地企业级 NVMe 延迟仅 15～94 微秒，云盘却高达 10～40 毫秒；小实例半数内存被 Java Agent 吞噬，高可用备库收双倍钱却禁读。默认监控仅分钟级不足百项（专业自建逾三千项），遇故障反而推销每月 6000 元的诊断包，甚至出过单机房喷水拖死全区管控 API 的闹剧。

### 为什么云 RDS 永久阉割了 PG 的生态灵魂？ {#rds-castrates-pg-extensions}

PostgreSQL 独步天下的灵魂是通吃时序、地理、列存与检索的扩展生态，但 16 个核心扩展横评中 AWS 与阿里云 RDS 仅支持 5 个，TimescaleDB、Citus 等悉数缺席。真实死穴在于新兴强力扩展普遍采用 AGPLv3 协议，云平台一旦集成托管就得开源其闭源管控摇钱树；而企业自建仅经 SQL 调用毫无传染风险，可零成本解锁 230 余个完整扩展。

### 嵌入式列存引擎为何能让单机 PG 迈向混合分析？ {#pg-duckdb-htap}

过去在事务库上跑重度分析，要么折腾脆弱的外部 CDC 同步链路，要么被云厂商捆绑推销昂贵的专有数仓。MotherDuck 与 Hydra 打造的 `pg_duckdb` 及 `pg_mooncake` 直接将向量化列存引擎缝合进 PostgreSQL 进程内原地高速扫表；这种零外部同步的进程内融合打开了单机实用化 HTAP 大门，更衬出禁装扩展的云 RDS 僵化落伍。

- [阿里云rds_duckdb：致敬还是抄袭？ · 关于 PG DuckDB](/cloud/rds-duckdb/#关于-pg-duckdb)

### 纯血布道者为何被边缘化，中国 PG 靠什么长成？ {#cloud-fork-vs-pure-pg}

云厂内部长期横亘“纯血托管 RDS”与“魔改自研 PolarDB”的路线之争：前者靠“提工单没用、找德哥管用”的专家信用留客，后者毛利高、绑定深还能讲国产故事，重心倾斜后纯血拓荒者注定边缘化。但凭制造业、PostGIS 刚需、去 O 与 AI 驱动，中国 PG 正以近 100% 年增速独立成林，早已不看单一云厂脸色。

## 二、黑箱暗门、外行工单与删库防线 {#rds-outages-and-blackbox}

### 为什么看一眼活跃事务表就能把云数据库查崩？ {#innodb-trx-latch-avalanche}

直到 MySQL 8.4，查询 `information_schema.innodb_trx` 仍会举起全局排他闩锁冻结全实例行锁，并在锁内遍历上千连接深拷贝活跃 SQL，高并发下极易拖成数秒引发雪崩。监控第一铁律是绝不改变被监控对象的死活：采集周期须守住 10 秒级，单条 SQL 强制带 100 毫秒硬超时，且总超时严格小于采集周期，确保极端卡顿也绝不垮库。

### 手动升级为何防不住暗门，盲目切换捅了什么娄子？ {#hidden-backdoor-and-blind-ha}

黑盒 RDS 的“手动升级”拦不住云厂商从暗门静默塞入问题采集器，事后连审计日志都捞不出肇事 SQL。更糟的是粗糙探针不分“卡慢”与“死机”，三次失败便拉闸斩断 2000 个连接，逼新主库顶着空缓存冷启动爬坡数十分钟。托管交出的只是复杂性，留给你的全是断服风险与一句“如无影响，请忽略”。

### 云售后如何把自家软件缺陷演成“莆田系扩容”？ {#putian-style-rds-support}

PG 采用固定共享内存配内核页缓存的双缓冲架构，读扫描绝不会吃崩内存；云售后却外行误诊诱导耗时三小时付费扩容，家酿脚本还乱改参数搞死从库。随后自家归档卡 Bug 堆积 800GB 日志，工单竟咬定磁盘打满，趁机推销年增收 12 万元的高价云盘——领教一回这种趁病创收便对云彻底祛魅。

### 买了云数据库为何还会删库归零，该如何设防？ {#pitr-and-delayed-standby}

实时主从复制只防坏盘不防误删，`DROP DATABASE` 会瞬间同步让热备同归于尽。本地一行配置加几分钱对象存储就能搞定的 WAL 归档与时间点恢复（PITR），在乞丐版云 RDS 上却被刻意阉割并封死登机抢救权限。正规生产库必须默认开箱即用“全量冷备 + 持续 WAL 归档”守住回溯底线，再配滞后数小时的“延迟从库”把大库误删 RTO 压至秒级。
