软件工程最大的敌人从来不是业务规模，而是脱离真实约束的虚荣架构与概念收租。现代硬件早已把单机容量与吞吐推高了三个数量级，但行业却仍在把专属于 1% 巨头的分布式分片、微服务拆分、独立湖仓 Catalog 乃至套了哲学外皮的“本体论”兜售给所有人。本篇剥离厂商公关迷雾，回归硬件物理定律、ROI 硬账本与并发编码基石，系统阐明以 PostgreSQL 与 DuckDB 为核心的极简主义架构哲学。

## 一、分布式伪需求、微服务反思与极简主义 {#distributed-and-minimalism}

### 为什么分布式 OLTP 对 99% 的企业都是伪需求？ {#distributed-oltp-myth}

分布式事务数据库的核心权衡是“以质换量”：为了水平扩展，不得不阉割复杂 SQL 与存储过程，跨节点 Raft/Paxos 共识 RPC 让同等硬件吞吐折损 70% 以上，CN/DN/TSO 多组件更引入了成倍的排障复杂度。而过去十年企业级 NVMe SSD 性价比暴涨千倍，每 TB 年折旧跌破 200 元，Gen5 单卡容量达 256 TB 且具数百万 IOPS；一台不到十万元的 64 核服务器跑单机 PostgreSQL 就能扛住百万点写、两百万点查与 32 TB 大表，连 OpenAI 核心业务也仅靠一主四十余从的经典 PG 集群支撑。OLTP 本质是延迟敏感的“工作记忆”，99% 的企业终生摸不到单机天花板，盲目上分布式纯属过早优化。

- [分布式数据库是不是伪需求？ · 新硬件的冲击](/db/distributive-bullshit/#新硬件的冲击)：核算企业级 NVMe SSD 十年性价比跃升千倍的账本，实证十万元内 64 核单机 PG 支撑百万 QPS 与 32 TB 大表的能力。
- [分布式数据库是不是伪需求？ · 伪需求的困境](/db/distributive-bullshit/#伪需求的困境)：区分 OLAP 与 OLTP“工作记忆”属性，论证 99% 业务终生无需跨节点事务分片的现实边界。
- [Andy Pavlo：2025 数据库世界年度总结 · 二、分布式的 PG 是伪需求吗？](/db/db-in-2025/#二分布式的-pg-是伪需求吗)：结合 Gen5 NVMe 单卡 256 TB 硬件红利与 OpenAI 一主四十从架构实例，剖析历代分布式 PG 始终难成主流的根因。

### 连亚马逊都在弃用微服务，过度拆分的泡沫为何集中破灭？ {#microservices-bad-idea}

正如 DHH 援引亚马逊 Prime Video 音视频监控团队的复盘所示，他们最初搭建的 Serverless 微服务在仅达预期负载 5% 时就撞上硬性扩展墙，重构回单体后运营成本直接骤降 90%。跨部门公开 API 本是巨无霸企业替代跨团队开会的组织解耦手段，强塞进单一团队维护的连贯应用里，用昂贵脆弱的网络调用取代本地函数调用，不过是每隔几年借尸还魂的“僵尸架构”，彻底违背了加尔定律——复杂系统只能从健康的简单单体演化而来。Twitter 裁员 90% 仍平稳运转撕下了技术冗余的遮羞布，在降本增效周期里，一切经不起 ROI 秤杆检验的云原生与拆分泡沫都必须出清。

### 当基础软件忙于标书打勾与套壳忽悠，会酿成什么隐形危机？ {#immune-system-silent-exit}

数据库行业充斥着“大炼钢铁”式的国产套壳换皮、把有状态数据库硬塞进 K8s 以及高价云 RDS 的焦虑营销，但基础软件公司最致命的衰败往往在报表上看不出来。早年那群挑剔难伺候、一遇隐患就发帖骂娘的一线开发者，其实是系统最宝贵的“免疫系统”；当产品演进从“开发者用着爽”异化成“招标评分表打勾多”、文档写成宣传册且工单响应比用户自己排查还慢时，懂行的人不会再去争吵，而是算清托管溢价假账后默默拉下真开源软件自建高可用与监控。这批人虽不贡献多少直接营收，可一旦撤离，产品的技术判断力就彻底空了。

### 为什么“先优化碳基程序员，再优化硅基芯片”才算得过账？ {#bio-core-over-cpu-core}

DHH 算过一笔极清醒的经济账：一名年薪 20 万美元的程序员（稀缺昂贵的碳基 BIO 核），成本等于在 Hetzner 租用 3663 颗 AMD EPYC 硅基核（单核年租金仅 55 美元）；只要把碳基核效率提升 25%，省下的钱就抵得上近千颗硅基核。放到数据库领域同样如此：今天绝大多数业务的瓶颈早已不是硅基 I/O 或百万 TPS 极限，而是开发者与 DBA 的认知带宽。当开源 PostgreSQL 内核足够成熟免费时，死磕纯自研内核正像 PC 制造业一样沦为赚五个点微利的代工苦活；真正的高科技溢价，全在 AWS RDS、Supabase 与 Pigsty 这类解放“碳基大脑”的管控层上。

## 二、小数据复兴、DuckDB 崛起与 HTAP 真相 {#small-data-duckdb-htap}

### 为什么说行业在分布式大数据上白白错付了十年？ {#small-data-lost-decade}

真实企业的分析数据远没厂商渲染得那么大。DuckDB 联合创始人 Hannes Mühleisen 援引 Redshift 与 Snowflake 生产统计指出，查询扫描中位数仅约 100 MB，99.9 分位也不到 300 GB。他把现代 DuckDB 装进降级回 2012 年系统的初代 Retina MacBook Pro（16 GB 内存），靠外存溢出落盘就跑完了 265 GB、60 亿行 TPC-H SF1000 全套 22 条查询，单条仅数分钟至半小时——当年光等 Hadoop YARN 调度报错都不止这点时间；换到 M3 Max 后几何平均耗时更从 218 秒骤降至 12 秒。矢量化引擎 2005 年便已问世，支持外存溢出的单机列存本可让行业少走十年分布式弯路。

- [小数据的失落十年：分布式分析的错付 · 基准测试](/db/smalldata-decade/#基准测试)：引用 Redshift 与 Snowflake 扫描中位数 100 MB、99.9 分位不足 300 GB 的生产分布，实证 99% 分析负载可单机承载。
- [小数据的失落十年：分布式分析的错付 · 讨论](/db/smalldata-decade/#讨论)：展示 2012 款 16 GB 内存 MacBook Pro 借外存溢出跑完 60 亿行 TPC-H SF1000 的实测数据，反思十年 Hadoop 弯路。
- [小数据的失落十年：分布式分析的错付 · 2023 年的改进](/db/smalldata-decade/#2023-年的改进)：对比 2012 款与 M3 Max 笔记本 20 倍查询提速账本，指出突破物理内存上限的外存执行才是单机吃下大数据的质变关键。

### 为什么分布式 HTAP 在真实企业里成了无人鼓掌的演出？ {#htap-no-applause}

厂商鼓吹“一套分布式 HTAP 兼顾交易与分析以省钱降维”，但客座作者瑞典马工从组织与架构双视角拆穿了这一幻觉：管 OLTP 的业务研发与管 OLAP 的数据平台隔着八道部门墙，没人愿背跨部门合并的锅；现代数仓塞满埋点日志与外部数据，交易库仅占一角，且微服务奉行独立库，强行融合是 `N+1` 而非 `1+1`。行存点改与列存批扫物理互斥，分布式 HTAP 不过是把“OLTP + 同步管道 + OLAP”捆进一个盒子改叫“刀叉合一（Knork）”：跨越速运标杆实为 Flink 灌宽表纯跑 OLAP，作业帮样板更把核心交易留在 MySQL，还得堆大内存防 Full GC 专门伺候 OMS 同步链路。

- [HTAP数据库，一场无人鼓掌的演出 · 跨越速运](/db/htap-no-applause/#跨越速运)：剖析企业部门墙、多源异构数仓与微服务独立库现实，拆解跨越速运案例实为 Flink 写入宽表纯跑 OLAP 的真相。
- [HTAP数据库，一场无人鼓掌的演出 · 作业帮](/db/htap-no-applause/#作业帮)：以“刀叉画框改叫 Knork”隐喻行存列存捆绑，揭露作业帮样板核心 OLTP 仍在 MySQL 且需重兵维护 OMS 同步管道的实况。

### 国产 NewSQL 热炒 HTAP 暴露了什么自救焦虑？ {#htap-efficiency-inversion}

国内分布式数据库扎堆翻炒 HTAP 与“单机分布式一体化”，本质是单机硬件极速 Scale-Up 证伪分布式 OLTP、且唯一用得上分片的互联网巨头拒绝为软件付费后的被迫自救。拉出硬账对比便知有多荒诞：普通现代笔记本用 DuckDB 6 分钟即可跑完 TPC-H 1000 仓；反观某国产分布式 HTAP 标杆官网评测，动用 92 核 478 GB 集群跑 50 仓的耗时，竟与 8～10 核笔记本跑 300 仓相当——砸十倍算力只干了六分之一的活，纯属行为艺术。反倒是从不炒概念的 PostgreSQL，早年靠逻辑复制双实例就能承载富士康工厂级混合负载，如今叠加 DuckDB 扩展更是极简兑现了真 HTAP。

### 为什么 PG 加 DuckDB 能终结库仓双轨制？ {#pg-kiss-duckdb}

把单机就能吊打集群的 DuckDB 魔改成 Smallpond 分布式框架，背离了“大数据已死”的极简灵魂；真正引爆地震的是“PostgreSQL + DuckDB”单机深度联姻。DuckDB 是分析界的 SQLite，单头文件加 MIT 协议就能在 ClickBench 主场压制 ClickHouse，但它剥离了鉴权、细粒度权限、高并发 MVCC、备份与高可用等企业管理骨架，而这恰是 PG 打磨数十年的看家本领。更妙的是 DuckDB 直接复用了 PG 语法解析器，双方又都是插件接口极开放的“可扩展性怪物”，吸引 `pg_duckdb`、`pg_mooncake` 争相入局。正如 `pgvector` 一年荡平独立向量库，二者合体必将终结脆弱昂贵的“关系库 + 独立数仓 + ETL”双轨制。

## 三、湖仓 Catalog 税与 Palantir“本体论”祛魅 {#catalog-and-ontology-bullshit}

### 为什么独立 Catalog 沦为收租层且有治理裂缝？ {#catalog-rent-and-security-gap}

剥去公关辞令，整个独立 Iceberg REST Catalog 行业本质上就是一张套了 REST 壳、按百万次请求收 `UPDATE` 租金的 PostgreSQL 表。Iceberg 乐观并发提交唯一不可替代的动作，只是对当前元数据指针做一次单行比较并交换（CAS），Polaris、Lakekeeper、Hive Metastore 底层存状态的照样是 PG 或 MySQL；2024 年 S3 原生支持条件写后，外部协调者的技术必要性正在消退，厂商却顺势将其包装成新的按次计费入口。更致命的是“控制面不在数据路径上”：Catalog 签发完前缀级短期 STS Token 即退出链路，客户端凭凭证可直读整个 Parquet 文件的全部字节，导致存储层行列权限失效，即时 `REVOKE` 也只能干等 Token 过期。

### 为什么把湖仓元数据放回关系库，单机四级阶梯就够用了？ {#metadata-in-db-and-pg-duckdb}

大数据折腾二十年耗资数百亿，只是把单进程数据库拆成十几个分别采购的组件，在对象存储上重造了一遍残缺的 System R。一旦像 DuckLake（28 张 SQL 表）或 `pg_lake` 那样承认“Catalog 本该是一张数据库表”，不再往 S3 撒满地 JSON 与 Avro 清单，高频小规模增删就能直接内联（Inlining）进表，瞬间把事务吞吐拉升百倍，跨表原子事务也成了现成白送的能力。对 99% 的企业而言，根本不必伺候 Spark/Trino 集群：给 PG 穿上 DuckDB 列存马甲，沿“单机 PG → 单机 DuckDB → DuckDB 加对象存储 → PG 管元数据的湖仓”四级阶梯演进，配双 100GbE 与 NVMe，单机跑得比八节点集群还快。

## 四、数据库即业务架构与超融合扩展生态 {#db-as-architecture}

### 为什么软件架构正向数据库坍缩，重回库内写逻辑可行吗？ {#db-is-the-arch}

Stonebraker 早有断言：“看软件架构对业务一无所知，看数据模型便知业务全貌”；纳德拉也直言现代应用不过是精美的数据库操作界面。过去拆出三层架构，是因为单机几万 TPS 捉襟见肘且手写存储过程门槛高；如今单机算力大幅富余，大模型又精通存储过程，把业务逻辑甚至 Web 服务器塞回数据库重获可行性——例如塞入 33 个扩展直接监听 HTTP 的 Omnigres，既省掉网络往返延迟与并发争用，又把部署克隆简化为纯 SQL 与目录拷贝。随着 PG 靠插件吞掉专用库、Supabase 吃掉后端并拿下 80% 的 YC 创业公司，应用架构正螺旋回归 `Agent + Database` 的极简形态。

### 为什么自然语言写 SQL 频失灵，Agent 最缺什么？ {#text-to-sql-and-agent-acid}

公开榜单动辄八九十分的 Text-to-SQL，一进真实企业数仓就原形毕露。Stonebraker 在 MIT 等七座真实企业数仓上实测主流大模型，初始准确率为 0%，叠加 RAG 与查询拆解也仅勉强达 20%～30%——防火墙隔离、内部黑话（如用“Course 6.2”指代计算机系）、物化视图语义重叠与复杂多表连接，让模式匹配器 LLM 束手无策，顶层整合仍须回归精简 SQL 与优化器。更重要的是，当 Agent 从只读问答迈向锁库存、扣款、发货的跨系统读写编排，面对非确定性海森堡 Bug 绝不能无脑重头重试，把状态收归数据库、靠日志持久化恢复与 ACID/Saga 事务兜底才是核心基建。

### 如何一条 SQL 亚秒算完百万行 24 点？ {#sql-poker-24-and-extension}

在禁用存储过程与自定义函数的前提下用一条 SQL 算扑克 24 点，若实时展开四则运算与括号全排列纯属算力灾难。由于 4 张 1～10 牌面的无序组合极其有限，利用算术基本定理将 1～10 映射为前 10 个质数（2 至 29）求积，就能抹平出牌顺序生成唯一整数键，把复杂搜索降维成与 566 条有解字典 CTE 的单次 Merge Join，M1 单核扫完 100 万行仅耗时 0.58 秒。有趣的是，全量答案文本恰有 10018 字节，卡在比赛 10 KB 上限之外；MySQL 靠内核自带 `COMPRESS` 占了规则便宜，而坚守精简内核的 PG 将压缩交由 `pgsql-gzip` 扩展实现（压后 7796 字节）——禁用扩展评判 PG 无异于自缚手脚。

### 既然多进程怕高并发，为什么 PG 不内置连接池？ {#why-no-builtin-pool}

PostgreSQL 遵循“一个程序只做好一件事”的 Unix 哲学，内核专注当好极致可靠的“发动机”，把突发连接缓冲、负载均衡、故障切换与读写分离交给外置“变速箱”（连接池）。直接拿裸内核怼上高并发生产，就像不装变速箱把发动机硬绑在车轮上路；但若把连接池硬塞进内核或强改多线程，又会破坏内核简洁性并丧失编排弹性。正确的工程解法是用 Pigsty 这类开源发行版做“整车交付”：将内核、pgBouncer、监控、备份与高可用预装一体并自动同步鉴权，让开发者默认连连接池端口无感用车。

- [你为什么不用连接池？ · PG 应该内置一个连接池吗？](/db/why-no-connection-pool/#pg-应该内置一个连接池吗)：以“发动机与变速箱”类比内核与外置连接池的职责边界，阐述发行版自动集成 pgBouncer 实现整车交付的工程正道。

## 五、现代硬件红利、云存储边界与本地主权 {#hardware-storage-and-homelab}

### 对象存储能全面取代本地磁盘吗？适用边界到底在哪？ {#object-storage-vs-local-nvme}

Kleppmann 与 Riccomini 指出了新一代分析系统纷纷建在 S3 上的诱因：不仅能花钱把坏盘与分区运维外包出去，更因 S3/GCS 支持强一致性与原子比较并交换（CAS）后，免装 ZooKeeper 或 etcd 就能直接搭起分布式栅栏、队列与预写日志。但我要泼三盆冷水：第一，S3 几十毫秒延迟比本地 NVMe 慢三到四个数量级，物理定律锁死它只适合做 OLAP 与日志底座，亚毫秒 OLTP 热路径仍必须靠本地盘与缓存；第二，免运维省不下高昂的 S3 API 调用与跨区流量账单；第三，国内大量政企自建机房、信创约束与本土对象存储语义差异，决定了不能盲目照搬“一切跑在 S3 上”。

### RDMA 与智能 SSD 潜力巨大，为何云上难产新库？ {#modern-hardware-cloud-deadlock}

正如 Alex Miller 所梳理，数据库服务端约 60% CPU 耗在内核 TCP/IP 栈上，换 QUIC 于事无补，唯有把读写与 CAS 卸载至网卡的 RDMA（远程读从超 100 微秒压至 1 微秒）与 SmartNIC 才能解锁可扩展 2PL+2PC 与跨节点共享缓存；存储侧沿去 FTL 的 ZNS/FDP 降写放大与 NVMe 盘内 CAS/SmartSSD 下推双线演进；计算侧 Unikernel 助事务引擎接管虚拟内存，而 GPU/FPGA 分析始终困在显存与 PCIe 带宽墙内。讽刺的是，欧美云巨头内部独享 RDMA 十年，对外却只卖阉割指令的通用实例（唯独阿里云开放通用 eRDMA 与 SmartSSD），“云上买不到新硬件就没人写新库”的死循环卡死了下一代数据库。

## 六、并发隔离、一致性迷雾与时间编码基石 {#concurrency-consistency-primitives}

### 一致性与 CAP 被误读多久，分布式为何靠共识？ {#consistency-cap-and-consensus}

“一致性”是极度过载的词：ACID 里的 C 指应用层自定义的业务不变量（分布式事务下体现为跨节点同生共死）；而 CAP 里的 C 是严格数学定义的“线性一致性”，要求多副本表现如单副本，一旦读到新值就绝不再见旧值。Kleppmann 早已点破，CAP 对可用性的极端定义脱离了现实 99.99% 延迟 SLA，当年走红纯属给 NoSQL 弱一致性做营销背书，工程设计更应追问断网能否读写的“离线可用性”。分布式事务本身靠单点协调者跑 2PC 就能保一致，引入等价于全序广播的 Raft/Paxos 共识，是为了在协调者宕机时无分歧选出新主以堵住可用性死穴。

- [一致性：过载的术语 · 具体来讲](/db/consistency/#具体来讲)：阐明 2PC 单点协调与共识算法的分工，揭示 Paxos/Raft 通过等价全序广播解决协调者单点故障可用性瓶颈的机理。

### 形式化验证与确定性测试难落地，基础软件靠什么守住质量？ {#formal-verification-vs-battle-testing}

Kleppmann 与 Riccomini 道出了实情：TLA+ 或 Isabelle 九成的价值在跑检查器之前——逼着人类向机器严谨写清系统假设并撞破思维盲区时就已兑现；AI 时代拿慢速参考实现当“测试预言机”配确定性模拟测试（DST）校验模型重写的高性能代码正打开新路。但残酷现实是：99% 的团队连备份恢复与主从切换演练都没做过，高级测试更困在“早期生死未卜不值得投、活下来后用户报 Bug 比补跑 DST 更快”（如 SlateDB 补做 DST 抓出的三个 Bug 用户早报过了）的悖论里。像 PostgreSQL 与 Pigsty 这样靠庞大真实生产用户踩遍极端边界并快速闭环，才是终极防线。

### 站在数据库内核视角，如何对区块链与智能合约彻底祛魅？ {#blockchain-byzantine-wal}

剥去投机炒作外壳，区块链在数据结构上与数据库预写式日志（WAL / Binlog）同出一源：区块即附带前序哈希指纹的只追加日志段，从创世块重放全量日志即可还原任意时刻状态，所谓“智能合约”不过是跑在这套分布式库里的存储过程。“去中心化”对应基于工作量共识的无主复制，“防篡改”则是借哈希链与最长链规则令伪造历史日志的算力成本在概率上不可行，实现抗恶意节点的拜占庭容错。除共识博弈极巧外，区块链的吞吐、查询与工程完备度离生产级分布式数据库还差十万八千里，且全网公示防抵赖刚需多属公权力监管地盘，盲目搞商业应用大概率沦为先烈。

### 为何 SQL 隔离级别名实错位，读已提交也毁备份？ {#isolation-levels-and-read-skew}

绝不能只看 SQL-92 隔离级别名称就高枕无忧：标准仅用脏读、不可重复读与幻读贴标签，暗绑早年锁调度假设，导致现代 MVCC 库严重名实错位——Oracle 11g 的 `SERIALIZABLE` 与 PostgreSQL 的 `REPEATABLE READ` 实为快照隔离（SI），而 MySQL/InnoDB 的 `RR` 连单行丢失更新（P4）都拦不住，按现代偏序模型甚至算不上真 SI。更危险的是默认“读已提交（RC）”仅给语句级快照：并发转账在只读查询先后扫两账户的间隙提交，就会读出总额增减的“读偏差（A5A）”；若跑数小时在线备份或全局对账，临时读偏差会固化为永久烂账，必须用事务级一致性快照根除。

### 快照隔离为何防不住“写偏差”，工程上该如何根治跨行异常？ {#write-skew-and-ssi}

PostgreSQL 快照隔离（SI）虽能自动回滚同行并发修改以拦截“丢失更新（P4）”，却栽在跨行盲区上：在“至少一人值班”场景中，两名值班员同时从一致快照看到两人在岗，随后各自更新自己那一行并双双提交，导致零人在岗——因写入行不重叠，SI 行级冲突检测失明，放纵了“写偏差（A5B）”。根治跨行异常只有两条正途：要么在 SI 下对查询前提涉及的所有行显式加 `SELECT FOR UPDATE` 悲观锁，把跨行依赖物化为行冲突；要么直接开启 PG 基于可串行化快照隔离（SSI）的 `SERIALIZABLE`，无阻塞追踪读写依赖环并在提交瞬间精准回滚枢轴事务。

### 为何会有闰秒与 2038 大限，PG 存时间有何坑？ {#leap-seconds-2038-timestamptz}

地球自转缓慢变慢导致天文 GMT 秒比铯原子钟 TAI 秒略长；协调世界时（UTC）在误差逼近 0.9 秒时插入正闰秒造出 `23:59:60` 的 61 秒分钟，常令缺防护的程序因时钟回拨崩溃。Unix 时间戳忽略闰秒死守“每日恒 86400 秒”，但仍停在 4 字节有符号整型的遗留类型（如 MySQL `TIMESTAMP`）将在 2038 年溢出罢工。PostgreSQL 用 8 字节微秒整型实现 `TIMESTAMPTZ`（跨度 29 万年且精准算对闰日），但切忌用 `::TIMESTAMP` 强转丢弃时区，更严禁在 `AT TIME ZONE` 后传 `'+1'` 等数字字符串——PG 会按 POSIX 区间反向重算，必须传具名时区或统一存 UTC。

### 为何 UTF-16 沦为包袱，UTF-8 成了编码通解？ {#utf8-vs-utf16-encoding}

屏幕“字形”绝不等于语义“抽象字符”（如 `é` 有单码位与组合两种表示），Unicode 必须分层解耦码位、定宽码元与字节序。早期 Java、JS 与 Windows 选用的 UTF-16 误判 65536 个状态够用，被汉字与 Emoji 打爆后打上“代理对”补丁变成变长编码——既丢了随机下标访问优势，又背着大小端 BOM 与单码元截断乱码包袱。反观 UTF-8 以单字节 `uint8` 为码元，根除端序歧义、100% 兼容 ASCII，且首字节与后续 `10xxxxxx` 字节前缀绝不重叠，坏块丢字节后下一字符瞬间自同步；语言模型上 Go 分清 `byte`/`rune`/`string` 堪称典范，把字节串叫 `str` 的 Python 2 则是灾难反例。
